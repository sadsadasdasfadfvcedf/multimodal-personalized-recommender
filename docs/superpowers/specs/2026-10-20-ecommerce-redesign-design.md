# 多模态个性化推荐助手 · 电商化体验重做设计

- 日期：2026-10-20
- 状态：已实施，阶段 1~6 回归与网页验收通过
- 范围：前端体验重构 + 必要的接口适配
- 目标：以六个阶段任务书为唯一功能边界，把现有能力组织成用户熟悉的电商购物流程

## 1. 目标与边界

### 1.1 目标

把当前“课程演示页 + 推荐接口”的界面，重做成用户熟悉的电商导购体验：

```text
打开页面
→ 商品瀑布流 + 右侧推荐助手
→ 用户对助手说需求
→ 助手理解并推荐，瀑布流同步更新
→ 点击商品进入详情
→ 查看证据与解释
→ 对比 / 点赞（收藏）
→ 继续追问
→ 反馈前后 TopK 对照
→ 阶段6验收
```

用户应该始终知道：

1. 现在在看什么商品
2. 系统为什么推荐它
3. 这次操作有没有生效
4. 下一步可以做什么

### 1.2 终点

终点是阶段5的反馈闭环 + 阶段6的端到端验收，不是下单。

```text
推荐 → 解释 → 对比 → 点赞/倒赞/浏览 → 反馈前后对照 → 验收
```

### 1.3 明确不做

不新增以下业务功能：

- 购物车
- 结算、支付
- 订单、物流
- 地址、会员、优惠券
- 独立收藏夹（收藏使用点赞/喜欢表达）
- 新商品数据源
- 新的推荐模型或新的排序算法
- ✌️/✋/☝️/👇 等扩展手势动作
- 额外的前端框架或 CDN 依赖

## 2. 六个阶段的验收映射

| 阶段 | 必须保留的能力 | 页面落点 |
|---|---|---|
| 阶段1 | 统一事件、请求、响应契约；非法输入明确错误；离线降级 | 状态抽屉显示推荐/多模态/LLM 模式；错误提示可读 |
| 阶段2 | 六类意图、槽位、缺失槽位不臆测、冲突、会话上下文、撤销 | 助手输入、槽位 chip、澄清卡片、撤销/重来、继续追问 |
| 阶段3 | 多路召回、来源可追溯、硬约束过滤、上下文重排、空结果降级 | 商品瀑布流、来源与证据标记、排序变化提示、加载更多 |
| 阶段4 | EvidencePack、可核验解释、无证据不编造、文本/语音呈现 | 商品详情中的推荐理由、证据列表、按需语音播报 |
| 阶段5 | 点赞/倒赞/浏览、正负互斥、反馈前后 A/B、会话隔离 | 卡片点赞、详情点赞、倒赞移除、撤销、状态抽屉 |
| 阶段6 | voice/vision/gesture 三类输入、故障降级、隐私检查、可复现 | 语音/画面/详情手势、故障提示、状态面板、验收脚本 |

## 3. 用户体验设计

### 3.1 桌面布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 品牌        搜索/说需求       账户        状态               │
├───────────────────────────────────┬──────────────────────────┤
│                                   │                          │
│        商品瀑布流                 │      推荐助手            │
│  卡片：图片 / 价格 / 证据 / 点赞   │  对话 / 槽位 / 结果      │
│                                   │  操作反馈 / 继续追问      │
│                                   │                          │
├───────────────────────────────────┴──────────────────────────┤
│ 对比栏：已选商品 × N        [开始对比]                       │
└──────────────────────────────────────────────────────────────┘
```

- 左侧占主要宽度，只展示商品，不承载长对话。
- 右侧助手固定宽度，保持对话上下文。
- 商品详情使用大尺寸模态层，不跳转新页面。
- 对比栏固定在底部，选中商品后出现。

### 3.2 窄屏布局

- 商品瀑布流为主视图。
- 助手变成底部抽屉或底部 Tab。
- 商品详情变成全屏 Sheet。
- 对比栏在底部 Tab 上方出现。

### 3.3 商品卡片

每张卡只保留高频信息：

- 商品图
- 标题
- 价格
- 推荐匹配度
- 1~2 个标签：命中条件 / 证据条数 / 类目
- 常驻 👍 / 👎
- 加入对比

卡片不展示长解释。长解释放入详情。

### 3.4 商品详情

详情采用“左图右信息”的大模态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 关闭                                                         │
│ ┌──────────────┐  标题 / 中英标题 / 价格 / 来源             │
│ │              │  推荐理由（逐句有据）                       │
│ │   商品大图    │  证据列表                                   │
│ │              │  [👍 喜欢] [👎 不喜欢] [加入对比] [追问此商品]│
│ └──────────────┘  相似商品（可继续下钻）                     │
└──────────────────────────────────────────────────────────────┘
```

行为：

- 打开详情自动记录一次“继续浏览”（阶段5弱反馈）。
- 点击“追问此商品”把焦点设为当前商品，并聚焦助手输入框。
- 详情内点赞/倒赞与卡片行为一致，复用同一反馈链路。
- 详情内不出现主页面手势按钮；手势直播在详情内自动开启。

### 3.5 对比

- 最多选择 4 件商品。
- 对比栏显示缩略图、标题、价格、移除按钮。
- 对比表至少展示：类目、价格、颜色/场景、推荐来源、推荐分。
- 差异单元格高亮。
- 对比是阶段2 `compare` 意图的 UI 入口，不新增业务语义。
- 点击“对比”但不足 2 件时，必须显示**用户可见**的提示（浮层或助手消息），并引导用户先点“加入对比”；不能只写入 `aria-live` 的视觉隐藏区域。
- 选择 2~4 件后，点击“对比”必须打开对比表；按钮不可无响应。

### 3.6 继续追问

“继续追问”不是新功能，是阶段2 SessionContext 的入口：

- 保留上一轮约束和焦点商品。
- 用户可继续输入“那黑色的呢”“为什么推荐这个”“和刚才那个比呢”。
- 继续追问时，助手消息要显示当前生效条件。
- 支持撤销和重来。

## 4. 反馈交互设计

### 4.1 点赞

```text
点击 👍
→ 卡片立即高亮（乐观更新）
→ 请求 /api/feedback
→ 助手显示“已记录 点赞 → 商品名”
→ 展示排序变化：有/无
→ 状态抽屉更新“已点赞”
```

再次点击同一个 👍：

```text
→ 取消点赞
→ 卡片取消高亮
→ 助手显示“已取消反馈”
```

### 4.2 倒赞

```text
点击 👎
→ 商品立即从瀑布流移除（乐观更新）
→ 请求 /api/feedback
→ 助手显示“已记录 倒赞”，并提供“撤销倒赞”
→ 后面的商品补位
```

再次点击同一个 👎：

- 如果卡片还在，直接取消倒赞。
- 如果卡片已被移除，使用助手消息里的“撤销倒赞”恢复商品并清除反馈。

### 4.3 不阻塞界面

反馈操作必须局部化：

- 只锁定当前卡片/按钮，不锁整个页面。
- 不等待 TTS。
- 不生成大体积解释包。
- 请求失败时只回滚当前卡片，并给出“重试”按钮。
- 用户可以在反馈请求进行时继续滚动或输入。

## 5. 前端架构

### 5.1 文件拆分

当前 `webui.py` 约 12 万字节，混合 HTML/CSS/JS/Python。重做为：

```text
webui.py                  # HTTP 服务、API 路由、静态文件服务
web/index.html            # 页面骨架
web/styles.css            # 视觉样式与响应式布局
web/app.js                # 页面状态与交互
```

约束：

- 不引入 npm、React、Vue、Tailwind 或 CDN。
- 继续使用 Python 标准库 HTTP 服务。
- 保持现有 API 路径不变。
- 静态资源只从项目内 `web/` 读取，禁止路径穿越。

### 5.2 页面状态

`web/app.js` 维护一份显式状态：

```js
state = {
  sessionId,
  items: [],
  filters: [],
  focusItemId,
  ratings: Map<itemId, 'up' | 'down'>,
  compare: Set<itemId>,
  pending: Set<itemId>,
  busy,
  mode
}
```

原则：

- 反馈只修改对应 item 的 `ratings` / `pending`。
- 搜索和推荐请求可以设置页面级 `busy`，但反馈请求不能。
- 任何网络失败都要回滚乐观更新。

### 5.3 后端 API 复用

不新增业务接口，继续使用：

- `GET /api/info`
- `GET /api/home`
- `POST /api/chat`
- `POST /api/more`
- `POST /api/feedback`
- `POST /api/view`
- `POST /api/products`
- `POST /api/voice`
- `POST /api/vision`
- `POST /api/gesture`
- `POST /api/camera/start|stop`
- `GET /api/camera/state`
- `GET /camera/stream`
- `GET /api/state`
- `POST /api/undo|reset`
- `POST /api/tts`
- `GET /api/img/{id}`
- `GET /audio/{name}`

只允许为支持新页面做轻量适配：

- 静态文件服务；
- 反馈取消（`polarity=none`）；
- 详情页需要的商品/证据字段整理。

### 5.4 模型与性能策略

流畅度优先从交互链路和异步边界解决，不把“换更大的模型”当作默认答案。

| 子系统 | 当前方案 | 本次是否更换 | 决策 |
|---|---|---|---|
| 对话 / 推荐解释 | DeepSeek `deepseek-flash` | 否 | 已在线，预热后通常 1~2 秒；继续使用，复杂问题再按需路由到更强模型 |
| ASR | SenseVoiceSmall 本地 | 否 | 识别本身已经很快；优先优化录音时长、VAD 和常驻进程 |
| VL | Qwen2-VL-2B 4bit 本地 | 暂不更换 | 是本地链路较重的部分；先按需加载、降低帧数/分辨率，确需更快再评估在线 VL |
| 推荐排序 | v146 XGBoost 制品 | 否 | 推荐本身约毫秒级，不是界面卡顿主因 |
| 手势 | MediaPipe | 否 | 保持本地实时识别，只保留 👍/👎 反馈 |

原则：

1. **先修 UI 和异步链路**：局部 pending、乐观更新、不阻塞 TTS、不返回大解释包。
2. **再做模型推理优化**：预热、按需加载、量化、缓存、减少输入帧数。
3. **最后才换模型**：只有基准测量证明模型推理是主要瓶颈时才更换。
4. 不因为换模型破坏六阶段验收、离线降级和既有协议。

## 6. 数据流

```text
用户输入
  → /api/chat
  → Orchestrator: 意图 → 槽位 → 会话合并
  → recall → hard filter → rank
  → EvidencePack → 解释
  → 返回 recommendations + trace
  → 瀑布流 + 助手同步更新

用户点赞/倒赞
  → /api/feedback
  → SessionContext.add_feedback / remove_feedback
  → 重新召回与排序
  → 返回 lightweight recommendations + before_after
  → 局部更新卡片 / 移除商品 / 撤销按钮

打开详情
  → /api/view（记录浏览）
  → /api/product/{id}
  → 详情展示证据、解释、相似商品
```

## 7. 错误与降级

| 场景 | 用户看到什么 | 系统行为 |
|---|---|---|
| 推荐服务不可用 | 状态提示“已降级为发布制品/离线快照” | 保留商品与解释，不空白 |
| 反馈失败 | 当前卡片提示失败 + 重试 | 回滚乐观更新，不影响其他卡片 |
| 对比不足 2 件 | 可见提示“至少选择 2 件商品”，并指向“加入对比” | 不打开空对比表 |
| 无推荐结果 | 收起货架，显示清晰空状态和下一步 | 不伪造商品 |
| 商品不存在 | 详情显示明确错误 | 关闭详情或提示返回 |
| 语音识别为空 | 提示“没听清，请重试或改用打字” | 不猜意图 |
| 手势未识别 | 提示手势比法 + 抓拍预览 | 不写反馈 |
| 在线 LLM 失败 | 对话降级提示 | 本地 Qwen 回退 |
| 网页搜索失败 | 显示搜索失败 | 仍可基于本地知识回答 |

## 8. 测试与验收

### 8.1 自动测试

每个改造阶段都必须保持：

```text
python -B scripts/run_all_offline.py      # 9/9
python -m pytest -q                       # 全部通过
python -m ruff check .
python -m ruff format --check .
python -m mypy

python scripts/13_webui_acceptance.py     # 19/19（反馈位置、倒赞确认、摄像头生命周期、详情、识图、追问）
```

### 8.2 手工验收

1. 打开页面：能看到商品瀑布流和助手。
2. 输入“500以内的婚礼装饰品”：货架更新，助手显示槽位和结果。
3. 点商品：详情打开，能看到图片、价格、推荐理由和证据。
4. 加入对比：底部对比栏出现，开始对比能看到字段差异。
5. 点赞：卡片高亮，助手显示已记录，不卡界面。
6. 再点点赞：取消点赞，状态恢复。
7. 倒赞：商品从货架移除，助手出现“撤销倒赞”。
8. 点撤销倒赞：商品恢复，反馈清空。
9. 继续追问：约束和焦点保留。
10. 语音/画面/详情手势：至少一条真实链路可运行。
11. 故障注入：推荐/多模态/TTS 至少一种降级有提示。
12. 状态抽屉：能看到已点赞、已倒赞、浏览、焦点商品和模式。

### 8.3 完成定义

同时满足以下条件才进入实现完成：

- 六阶段验收仍全部通过；
- 页面无全局反馈卡顿；
- 点赞/倒赞可取消；
- 倒赞商品立即移除；
- 详情解释逐句有据；
- 对比和继续追问可用；
- 不新增购物车、支付、订单等范围外功能。
